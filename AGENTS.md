# AGENTS.md — Technical Context for AI Agents

This file documents the architecture, key files, known gotchas, and current state of **Aiman** so that any AI coding agent can continue development without needing prior context.

---

## What Is Aiman?

Aiman is a **terminal UI (TUI) orchestrator** written in Go. It manages the full lifecycle of remote AI coding sessions:

- Turns a JIRA ticket into a git worktree + terminal session + mutagen sync + AI agent in one flow
- Tracks active sessions, provides live pane previews, git status, and AI summaries
- Supports Claude Code, Antigravity CLI, GitHub Copilot, Kilo Code, Cursor, Pi, Muse Code, and Deep Code as agents

Binary: `aiman` — built from `./cmd/aiman/main.go`  
Module: `github.com/bouwerp/aiman`  
Go: 1.26  
Current release: **v0.41.0**

## Build & Test

```bash
make ci          # fmt + vet + test + lint (full CI: run before every commit)
make eval        # deterministic harness evals (fake remote, temp DB and socket)
make build       # go build -o aiman ./cmd/aiman
go build ./...   # quick build check
go test ./...    # tests (skip -race if Go stdlib version mismatch)
```

`make eval` runs the cases under `evals/` against an in-process `aiman serve`,
a temp SQLite database and a temp Unix socket, with a fake remote and fake
creator. It needs no SSH host, agent binary or network, and removes its temp
directory. It covers lifecycle, steering, to-dos, handover, usage and the
verify pass/deny/reproduce paths. It is not part of `make ci`; CI runs it as a
separate five-minute job. Only the opt-in `-tags evalreal` track spends money,
and that track is nightly, cost-capped and never part of CI.

**Known pre-existing test failure:** `TestOllamaIntelligenceSummariseSession` in `internal/infra/ai` — requires a local Ollama instance, always fails in CI. Ignore it.

**Release process:**
```bash
git tag vX.Y.Z
git push origin vX.Y.Z
```
GitHub Actions builds cross-platform binaries and creates the release automatically. A final job then hashes the uploaded archives into `checksums.txt` (one `<sha256>  <asset>` line per `.tar.gz` / `.zip`; unsigned) and publishes it with `install.sh` as release assets. Installs refuse a tag until that job finishes.

Installs are pinned and verified. `Kind.InstallPipeAt(tag)` takes `install.sh` from that release and passes `VERSION=<tag>`; `install.sh` verifies the archive against that release's `checksums.txt` and exits non-zero with nothing installed on a mismatch or a missing file, and a pinned install never falls back to a source build. `aiman update` and `aiman downgrade` verify the same way (`downloadRelease`). The tag is the laptop's release for an install, the release it is moving to for an auto-update, the latest release for a manual `u`, and the latest release when a local build has no release of its own. **Releases published without `checksums.txt` cannot be installed by this code**, by `aiman downgrade` or by a pinned `install.sh`.

## The Session Data Model

A `domain.Session` holds:

| Field | Description |
|---|---|
| `ID` | UUID — primary key everywhere |
| `IssueKey` | JIRA key, e.g. `PROJ-123` |
| `Branch` | git branch name |
| `BaseBranch` | ref the worktree branch was cut from; basis for diffs against the base |
| `RepoName` | `owner/repo` GitHub slug |
| `RemoteHost` | SSH host (from config) |
| `WorktreePath` | absolute path to git worktree on the remote |
| `WorkingDirectory` | active sub-directory inside worktree (what the agent cwd is) |
| `TerminalName` | human-readable terminal name (the PTY is addressed by `ID`); sqlite column `tmux_session`, JSON key `TmuxSession` |
| `Backend` | `pty` for every session aiman runs, `tmux` for a legacy row, empty when no terminal is recorded |
| `MutagenSyncID` | mutagen sync session name (usually `aiman-sync-<ID>`) |
| `LocalPath` | `~/.aiman/work/<ID>` — local mutagen sync root |
| `AgentName` | agent binary name, e.g. `claude` |
| `AgentModel` | model shown in the TUI: the launch model, else the one detected at create; never passed to a launch |
| `LaunchModel` / `LaunchEffort` | per-launch model and effort from an `agents.smart` or `agents.preferred` entry (or an explicit `--model`/`--effort`); same-agent restart and revive reuse them, an agent switch clears them |
| `Tier` | model tier the session was created from: `smart` or `worker` after fallback; cleared with the launch model on an agent switch |
| `AgentSessionID` | vendor conversation id for resume (`claude --resume`, `grok --resume`, …) |
| `AgentSessionPath` | optional vendor transcript / session file |
| `AgentTitle` | vendor session title when a hook reports one |
| `AgentEnded` | SessionEnd: the agent finished (not a crashed pane) |
| `HookState` | last hook-reported idle/working/waiting_input, with source/message/seq |
| `Status` | `PROVISIONING → ACTIVE → CLEANUP` (or `ERROR`/`INACTIVE`) |
| `Tunnels` | local↔remote port forwards |
| `ReviewPR` | `owner/repo#n` for a session reviewing that pull request; empty otherwise. A review session is interactive; code that treats it differently checks `ReviewPR != ""` |
| `FixPR` | `owner/repo#n` for a fixer session (role `fixer`, visible) pushing to that PR's branch. The fixer never holds `ReviewPR`. The TUI refuses `c` for it, verify-before-PR skips it, and the meta line shows `fix #n` |
| `AWSProfileName` | legacy scoped AWS profile name retained only for migration/cleanup |

## SQLite Persistence — Critical Design Decision

**File:** `internal/infra/sqlite/repository.go`

The `Save` method uses `INSERT … ON CONFLICT(id) DO UPDATE SET`. As of **v0.6.57**, all critical session fields use:

```sql
field = COALESCE(NULLIF(excluded.field, ''), sessions.field)
```

**Why this matters:** The session discoverer (`Discover`) builds sessions from live remote state — it can only know what the PTY runtime and mutagen report. Fields like `Branch`, `AgentName`, `WorktreePath`, and `WorkingDirectory` will often be empty in discovered sessions. Before this fix, discovery was silently overwriting the DB with empty strings on every scan cycle, causing restart to fail with "session has no working directory".

**Fields protected by COALESCE:** `name`, `group_name`, `issue_key`, `branch`, `base_branch`, `repo_name`, `remote_host`, `worktree_path`, `working_directory`, `tmux_session`, `backend`, `mutagen_sync_id`, `local_path`, `agent_name`, `agent_model`, `launch_model`, `launch_effort`, `agent_session_id`, `agent_session_path`, `agent_title`, `agent_ended`, `hook_state`, `hook_state_message`, `hook_state_source`, `watch_pr`, `review_pr`, `fix_pr`, `role`, `issue_type`.

**Fields always overwritten:** `status`, `updated_at`.

**Fields with null-safe COALESCE (not empty-string):** `tunnels_json`, `aws_profile`, `aws_config_json`.

The `tmux_session` column keeps its name and holds `TerminalName`. `backend` is `pty`, `tmux` (a legacy row, `domain.BackendLegacyTmux`) or empty (no terminal recorded). Opening the DB sets a NULL `backend`, a row written before the column existed, to `tmux`; an empty value stays empty.

### WAL, pools and the session list cache

`NewRepository` opens the file twice: a writer `*sql.DB` (`DB()`, `SetMaxOpenConns(1)`, DSN `_txlock=immediate`) and a reader pool (`Reader()`, 8 connections, idle ones closed after a minute). Both DSNs carry `busy_timeout(5000)`, `journal_mode(WAL)` and `synchronous(NORMAL)`; pragmas go in the DSN because they are per connection. Read-only methods query the reader, mutating methods the writer. `contextstore.OpenIndex` and `memoryjob.Open` take `(writer, reader)` and run their `SELECT`s on the reader. A passive `wal_checkpoint` runs on the writer every 5 minutes; `Close` closes the readers, runs `wal_checkpoint(TRUNCATE)` (a busy answer, another process holding the file, is logged) and closes the writer. `aiman-trigger` (and a TUI run on the host) opens the same file as a separate process; WAL lets its writes and serve's reads coexist. The laptop TUI opens the laptop's own database.

`OnChange(fn)` runs `fn` after every mutating method commits: `ChangeIdentity` for an insert, a delete, `ClearNativeAgentIdentity`, or a `Save` that changes `name`, `group_name`, `parent_id`, `role`, `status`, `backend`, `branch`, `working_directory`, `review_pr` or `fix_pr` (read by primary key inside the same transaction before the upsert; an empty incoming field is no change because of the COALESCE), else `ChangeOther`. Hook reports are `ChangeOther`.

serve's `loadSessions` reads the stored rows through a cache (`storedSessions`, TTL `sessionListTTL`, 2s), invalidated on `ChangeIdentity`. `New` finds `OnChange` by interface assertion, so a wrapper embedding `*sqlite.Repository` works; a repository without it is never cached. The live pty merge runs per call. The TTL is what brings in another process's writes. `loadSessions` never writes: `Server.BackfillNames` names and groups nameless rows once at serve start, and `session.register` (any row whose name or group is empty) and `applyAgentReport` (rows it creates) backfill. A handler that needs a fresh hook field reads the row by id (`repo.Get`): `classify`, `applyAgentReport` and `steerSession`, the delivery gate's lookup. A handler that branches on a hook field over a list scan narrows by identity first and re-reads those rows' hook fields (`freshRows`): `liveReview` (review create) and `checkFixRounds` (`review.fix`); `admitPeer` re-reads its target (`freshHookFields`). `lockedTarget` (restart, terminate) overlays the target's row by id after taking the session lock (`sessionByID`), so a queued call sees the launch model, vendor id and ended flag the previous one wrote. `session.events`, `pty.list` and `host.stats` read the stored rows through the cache (identity fields only).

## Session Discovery

**File:** `internal/usecase/session_discoverer.go`

`Discover(ctx, host)` asks the remote serve for its PTY sessions (`ScanPTYSessions`, `aiman pty list` over SSH), adds worktrees with no live session and mutagen syncs with no session, overlays hook reports, and returns `[]domain.Session`. It never asks tmux. `ScanPTYSessions` returns an empty list for a remote with no aiman binary and `ErrServeDown` when serve does not answer. A failed scan, `ErrServeDown` included, fails the whole call, because the merge step reads the result as every session on the host and would otherwise mark known sessions dead.

It can only populate fields it can read live:

- `ID`, `TerminalName`, `WorkingDirectory`, `Backend` (`pty`) from the PTY record
- `Role` and `ParentID` from `pty.list`: serve's database row, else what the creator passed to `pty.create` (kept in the holder's `meta.json`, so a helper is hidden before its row is saved). The dashboard hides reviewer and handover children; an older serve sends neither
- `MutagenSyncID` and `LocalPath` from the matching mutagen sync (`mutagen sync list`), which also sets status `SYNCING`

It does **not** read `Name`, `Group`, `Branch`, `AgentName`, `IssueKey` or `WorktreePath`; those come from the DB. A row stored without a name (registered from the laptop or written by a hook) is named after its terminal, like a discovered one, never `impl`.

Serve's own `liveSessions` copies `Role` and `ParentID` from the holder, and `mergeLiveSessions` fills them into a stored row that has none. `session.report_agent_session` for an id with no row stores the live record, except for a hidden helper (reviewer, handover, consult): its agent reports seconds before the creator saves the row, so that report reaches the recorder, the steerer and the ledger but is not saved, and the creator's save is the first identity write.

Sessions merge by ID. Discovery keeps every live PTY session with an ID of its own even when two share a terminal name (children of one parent can). The dashboard merge (`lookupPersistedSession`) matches a stored row by ID first and falls back to `sessionTerminalKey` (host plus terminal name) only for rows without one. Preview captures, activity hints and git status are keyed by session ID. A selected session missing from one scan keeps its row for up to two scans.

A legacy tmux row is never discovered. It stays listed as inactive, in memory only, until the user stops it and restarts it into pty.

`applyDiscoveryResult` overlays those DB fields onto live sessions (`overlayPersistedSessionFields`) so a scan cannot flatten names and groups in the TUI. Save still uses COALESCE so empty discovery writes do not wipe the DB. Serve's non-empty name and group win over the laptop's in `session_created`, so the TUI's group assign, group rename and session rename save the laptop DB and also call `session.move` / `session.rename` on that session's serve (`syncIdentityToServe`, `internal/ui/session_identity_sync.go`); a failure toasts, an old serve or a `not_found` is silent.

The `discoveryResultMsg` handler in `dashboard.go` saves discovered sessions to DB after each discovery cycle. Empty discovered fields are safe because of the COALESCE fix.

Startup also prunes DB sessions whose explicit `RemoteHost` no longer matches any configured remote. This prevents deleted/retired remotes from resurrecting sticky orphaned sessions on restart.

## SSH Manager

**File:** `internal/infra/ssh/manager.go`

Key behaviours:
- Uses `ControlMaster=auto` + `ControlPersist=10m` — bulk calls to the same host share one socket, and the interactive attach has its own
- Socket path: `~/.aiman/sockets/ssh-<sha256(user@host)[:16]>-noagent.sock` for bulk calls, `ssh-<hash>.sock-tty` for interactive attach
- Only `AttachPTYSession` forwards the laptop's agent (`-A`, on its own master); every other call passes `ForwardAgent=no`, so a remote needs its own GitHub credentials for `git fetch`, `clone` and `push`.
- Per-call timeout: **30 seconds** (`Execute`). `ExecuteWithTimeout` is for work that exceeds that (remote install/update uses `remotesvc.OpTimeout`, 3 minutes).
- On transport errors: clears socket, retries up to 2×, then falls back to `ControlMaster=no`
- `ResetControlSocket()`: sends `ssh -O exit` to gracefully stop the master, then removes the socket file. Call this before disruptive remote operations (e.g. stopping a session) to ensure a clean connection for the next call.
- `CloseAttachMaster(ctx)` sends `ssh -O exit` to the attach (`-sock-tty`) master and removes its socket; the dashboard calls it in the background once an attach returns, so the forwarded agent is unreachable from the host after a detach. A missing master is not an error.
- A denial printed by the remote git (`ssh.IsRemoteGitAuthDenial`: `git@<host>: Permission denied`, or `Permission denied` with git's `fatal: Could not read from remote repository`) is not retried; `git.WrapRemoteError` turns it into `git.ErrHostAuthDenied`, whose message tells the operator to give the host its own GitHub credentials. The fetch, clone and pull paths in `internal/infra/git` wrap their errors with it.

**Do not** add "permission denied" removal from `isRetriableSSHTransportError` without testing — it causes 4× retries on auth failures which wastes 120s.

## Remote serve / trigger as a service

**File:** `internal/infra/remotesvc/remotesvc.go`

`aiman serve`, `aiman-trigger` and `aiman-gateway` run on remotes as systemd `--user` units (`aiman-serve.service`, `aiman-trigger.service`, `aiman-gateway.service`, all `Restart=on-failure`, `RestartSec=2`) with `loginctl enable-linger`. They are independent of the laptop TUI. `StartScript` (start, reload, update and the gateway lockstep) uses the unit whenever `systemctl --user show-environment` answers, writing the unit when it is missing and enabling it, so a daemon started under nohup moves to systemd at its next start or update. Only without user systemd does it fall back to a nohup supervisor: `nohupStart` writes `~/.aiman/<unit>-supervise.sh`, a loop that runs the binary and restarts it 2s after any exit, and `~/.aiman/{serve,trigger,gateway}.pid` names the supervisor. TERM or INT to the supervisor stops its child and the loop, so `StopScript`, `leftoverCleanup` and `nohupStart` stop supervision by killing the pid file's process before the `pkill`. serve's holders are setsid'd children of serve, never of the supervisor, and the trap signals only serve's pid, so they survive as before. The nohup log (`~/.aiman/<kind>.log`) is moved to `<log>.old` when over 10 MiB, before the start and before every restart; under systemd output goes to the journal. The probe reports a live supervisor as `DRIVER=nohup`, `ACTIVE=active` while the child runs and `activating` between restarts.

Admin Menu (`m`) → **Agent API** is the settings page for `aiman serve` (one row per remote). The Daemons tab (Tab) also lists **agent API** and **trigger**. The skill talks to the agent API only. Start it with `i` on that settings page.

| Key | Action |
|---|---|
| `i` | Install/enable (linger first, then the unit) |
| `s` | Start or restart |
| `c` | Reload (restart; serve re-reads remote `~/.aiman/config.yaml`) |
| `u` | Update binary from GitHub, then restart. Updating serve (`u` or auto-update) also updates `aiman-gateway` when it is installed on that host, restarting it only if it was running |
| `ctrl+k` | Stop |
| `t` | Install RTK and register its agent hooks (`internal/infra/rtk`) |
| `p` | Pair a phone: update `aiman-gateway` first when it is older than v0.25.0 (no `pair` subcommand) or reports no release number, start it if needed, run `aiman-gateway pair --json` under `timeout 30`, draw the QR (`internal/ui/gateway_pair.go`) |
| `r` | Probe driver/status/version/socket/logs |

`t` runs `rtk.InstallScript` under `remotesvc.OpTimeout` and reports an `rtkInstallMsg`, routed in `Update` next to `serviceOpMsg`; the model then re-probes serve. The serve probe prints `RTK=<version>` into `Daemon.RTKVersion`, which the page shows as `RTK: <version>` or `RTK: not installed (t to install)`. Hooks are registered only for `rtk.HookTargets` (Claude, Codex, Cursor, Gemini, Copilot, Pi). The `$` usage view runs `rtk.FetchGain` per host and appends `rtkGainLine` to `usageHost.extra`. Never run plain `rtk gain`: without `--format json` it can open a live dashboard. Never export `RTK_VERSION` into the install script's environment; RTK's `install.sh` reads it as a version pin.

Session create also calls `ensureRemoteServer` if `~/.aiman/aiman.sock` is missing.

On start, `aiman serve` installs or updates the bundled skill (`internal/aimanskill`) in user-level agent skill dirs under `$HOME` and in each known session worktree, and registers native-session hooks (`internal/agenthook`) in each installed agent's config. Identity agents (Claude, Grok, Cursor, Codex, Copilot, agy, Muse Code) report session id, `SessionEnd`, and `idle_prompt` where the runtime has it. Muse Code uses `SessionStart`, `Stop`, and `UserPromptSubmit` in `~/.config/muse/settings.json` (`schema_version` 1). After each hook install (serve start and every agent update) serve runs `codex app-server` in the background (`agenthook.TrustCodexHooks`, 20s cap) and trusts, through `config/batchWrite` on `hooks.state`, only the `hooks/list` entries whose command is an aiman hook script under `~/.aiman/hooks/` and whose status is untrusted or modified, so Codex does not ask for a hook review at launch. Other hooks, such as graphify's, stay for the user to review, and a failure is only logged. Kilo Code and Pi also report lifecycle state. Pi (pi.dev, `@earendil-works/pi-coding-agent` 1.4) gets `~/.pi/agent/extensions/aiman-native-session.ts`: `session_start` is idle with the session id and file, `agent_start` is working, `agent_settled` (not `agent_end`, which retries and queued work follow) is idle, `ui_prompt_start` is waiting_input, and `session_shutdown` with reason `quit` is the end. Plugin `seq` is `Date.now()`-based, because serve drops a report whose seq is below the last one applied. Pi resume is `pi --session <id>`; session files are `~/.pi/agent/sessions/--<cwd>--/<ts>_<id>.jsonl`. Pre-launch trust also writes the worktree into `~/.pi/agent/trust.json` (never flipping a `false`). Pi's model flag takes `provider/id:<thinking>`; `--thinking` (off…max) overrides that suffix, so aiman skips `--thinking` when the model carries a level. Deep Code has no hook API: `deepcode-launch.sh` runs `aiman session deepcode-watch` on `~/.deepcode/projects/<code>/sessions-index.json`, then the CLI. Resume is `deepcode --resume <uuid>`. Model and effort are `DEEPCODE_MODEL` and `DEEPCODE_REASONING_EFFORT`. Permissions stay the user's `defaultMode`. `session.wait` uses a hook report newer than 2 minutes instead of `pane.Classify`, except that a `working` report loses to a menu on screen (`pane.MenuOpen`). Hooks fire only at a turn's start and end, so a longer turn falls through to the rules; `classify` reads their `unknown` as `working` while `agenthook.TurnOpen` holds and the holder has recorded output, and the rules' silence check settles a turn whose agent died without a stop hook. Session create still writes the worktree skill copy. Ageni is not hooked.

`session.create` takes `name`, `branch` or both. `name` is free text; with no `branch`, serve derives one (`domain.BranchFromSessionName`, the TUI wizard's rule, else a generated `session-<time>-<rand>`) and adds `-2`, `-3`… while `CreateSession` fails `WORKTREE_EXISTS` (a named branch is not suffixed). With no `name` the session is named after the branch, suffixed if taken, or `q<n>` for `quick`. Parameters also include `tier`, `model` and `effort`: `tier` is exclusive with `agent`, and `model`/`effort` require an explicit `agent`. The result is `{"type":"session","session":{…,"tier":…},"requested_tier":…,"tier_fallback":…}`; `SessionInfo.Tier` carries the tier after fallback and `sessionFromInfo`/the remote-create result copy it.

`session.register` copies laptop sessions into serve's database. Identity fields come from the payload. When a row already exists, hook state, `AgentEnded`, `AgentTitle`, and `Status` stay on that row. A payload naming a different agent with no launch model clears the row's `launch_model` and `launch_effort` (`ClearLaunchModel`). `LocalPath`, `MutagenSyncID`, `Tunnels`, and `AWSConfig` are laptop-only and are dropped. Empty ids and ids with the `pending-` prefix are skipped. `dropSession` (terminate, forget, discard, consult retire, fixer, reviewer and review cleanup) leaves a tombstone in sqlite `forgotten_sessions` (`MarkForgotten`, with the reason), so a client's stale copy cannot bring the row back: register skips a tombstoned id with no stored row and no running holder and lists it in `forgotten`; a stored row or a running holder clears the tombstone (`ClearForgotten`) and registers it. A failed tombstone lookup counts as not forgotten. The result is `{"type":"sessions_registered","ids":[…],"forgotten":[…]}`; `ids` lists only registered rows. `usecase.RegisterSessionsOnRemote` returns `forgotten`, and the dashboard deletes those rows from the laptop database and its list (an older serve sends none). A session caller (`isSessionCall`) gets `needs_operator` and nothing is saved, because a registered `parent_id` would widen its scope.

`session.restart {session, agent, model?, effort?}` (CLI `aiman session restart <name> --agent x`, `internal/server/handlers_lifecycle.go`) returns `{"type":"session","session":…}` under `SessionRestartTimeout` (2 minutes) and runs `usecase.RestartSession`. `agent` is a command or display name; a value that is not a plain command, or an agent `agentInstalled` does not find, is `invalid_params`. `usecase.AdoptRestartAgent` decides a switch, treating a display name and its binary as one agent. A switch passes the target to the handover (`agent_switch`), clears the sidecar and `ClearNativeAgentIdentity`, and drops the launch model and effort unless the call names new ones. The same agent keeps its model, effort and vendor id unless overridden. The stored `AgentEnded` is cleared and `session.restarted` recorded. A legacy row is `legacy_terminal`, a hidden helper `invalid_params`, and a failed launch `create_failed`.

A consult with no usable report whose agent ended (`AgentEnded`), whose terminal is gone (`Tracker.Alive`, `Server.ConsultAlive`) or that ran past `handover.timeout` (`Tracker.ConsultTimeout`, default 10m, from `CreatedAt`) is given up: the item is unlinked and stays pending, the consult is retired, and the coordinator gets `[aiman] consult <id> for <todo> produced no report; ask again or proceed without it.` Each pass ends with a sweep that retires every consult older than one minute whose parent's list holds no open item linking it (an item settled before a retire, or a consult started but never linked).

Child brief and report: `coordinator.ParseBrief` requires exactly the seven headings `## Objective`, `## Contract`, `## Owns`, `## Out of scope`, `## Acceptance tests`, `## Report must contain` and `## Escalate when` (at least 8 words in all) and refuses the old three-heading form with a message naming them. `applyFor` defaults the child's base to the parent's branch only when the child's repository is the parent's (`repo` empty or equal to `RepoName` ignoring case); in another repository an empty base means that repository's default branch, and the branch is still `coordinator.ChildBranch`. `session.create --for` writes the brief into the child's `.aiman_task.md` between `<!-- aiman:brief -->` and `<!-- /aiman:brief -->` (`coordinator.BriefFromTaskFile` reads it back) followed by `coordinator.ChildGuidelines`: the brief is the design, do not wait for confirmation, do not edit the acceptance-test files, escalate when an Escalate when condition holds or the piece is harder than rated after exploring (`aiman todo add "<question>"`, then `session create --consult --for <todo-id> --brief-file <file>` with the three consult headings, then wait for the `[aiman]` note; the skill's `## Escalating (children too)` section, outside Design first, repeats this), write Evidence and Surprises. `ValidateReport` requires `## Evidence` (citing a repo path or a test command) and `## Surprises` (`none` allowed); without both the item stays open and the tracker steers the coordinator once. When a landed child's Surprises is not `none`, the tracker steers the coordinator once per child to re-read the design before starting dependent pieces. verify reads the brief from the worker's task file: `AcceptanceFiles` (repo paths in `## Acceptance tests`) are protected, and a diff touching one (edit, delete or rename away; `verify.TouchedProtected`, re-reading an untruncated patch) becomes a REQUIRED finding; `AcceptanceCommands` (backtick spans that are not paths) run at the review snapshot after the test command and each non-zero exit is a REQUIRED finding. `Review.AcceptanceCommands` and `Review.TouchedAcceptance` record both. A task with no brief is reviewed as before.

Local landing (`docs/specs/ci-minutes.md` Behaviour 1): `session.land {session}` (CLI `aiman land [--session NAME]`, `internal/server/handlers_land.go`, `SessionLandTimeout` 5 minutes, in `slowCall`; not a gateway device method) merges a child's `HEAD` onto its coordinator's branch without a PR. The target is `session`, else the caller; a session caller passes `refuseOutOfScope`, and a session with no parent (or a hidden helper or fixer) is `invalid_params`. Checks, in order: the parent's branch is not the repository's default branch (origin/HEAD in the main clone, `invalid_params`), `.aiman_report.md` passes `coordinator.ValidateReport`, the child's tree has no changed or untracked files (`worktree.Pending`, aiman's scaffolding excluded), verify passed for the tree when `verify.before_pr` is on (`Manager.ForTree`), and the local gate passed for `HEAD` when a `LandGate` is set (`Server.SetLandGate`; nil skips it). `git.Land` (`internal/infra/git/land.go`) then runs locally: a blocking flock on `~/.aiman/land/<owner>__<repo>@<flattened branch>.lock` (`git.LandLockName`) held across fetch, parent check, merge and push; the parent check (`symbolic-ref HEAD` is `refs/heads/<parent>`, `origin/<parent>..HEAD` empty, no tracked changes, any git failure) is `land_parent_diverged`, which also steers the coordinator `[aiman] child <name> is waiting to land on <branch>: push or stash your changes.`; a detached worktree at `origin/<parent>` under `~/.aiman/land/<child id>/` takes `merge --no-ff <sha>` as `Aiman <aiman@localhost>`; the main clone pushes `<merge sha>:refs/heads/<parent>` with `core.hooksPath=/dev/null`, never forced. A rejected push refetches and remerges up to 3 times, then `land_busy`; a conflict is `land_conflict` with `data.files`. The scratch tree is removed on every path and the child branch is never pushed. Only after the push serve records `child.landed` (child, parent branch, merge sha) on both ledgers and steers `[aiman] child <name> landed on <branch> at <sha>. Run git pull --ff-only.` `coordinator.child_prs` (`Config.CoordinatorChildPRs`, default false, pushed by `MarshalServeConfig`) picks the tracker's `landed`: false uses `Tracker.LandedLocal` only (`Server.LandedLocal`: the newest `child.landed` merge sha is an ancestor of `origin/<parent>` after a fetch, `git.LandedOn`) and never asks GitHub; true keeps the PR path.

Harness (`internal/harness`, `internal/server/handlers_harness.go`, `cmd/aiman/harness_serve.go`): a repository's `.aiman/harness.yaml` (`harness.FilePath`, version 1, at most 256 KiB, parsed strictly: an unknown key anywhere is `harness_invalid`) declares an `app` (`build`, `run`, named `ports`, `limits`), `services` (`image`, `env`, `ready`, `database` postgres or sqlite, `caps`, `root`, `limits`) and `scenarios` (`id`, `title`, `services`, `setup`, `fixtures`, `steps` with `do`/`expect` and `{{<port>}}` placeholders, `checks` with `name`, `run`, optional `image` and `debug`). Serve reads it from the commit with `git show`, never the working tree; `repos.<slug>.harness` in operator config replaces it and the run reports `source: config` (else `file`). `wireHarness` enables the methods when `harness.enabled` is not false and `docker` is on PATH; otherwise every `harness.*` answers `unavailable`. One `harness.Manager` per serve keeps runs under `~/.aiman/harness/<session>/<run>/` (`src`, `out`, `sandbox` with the compose file, `control`, `logs`, `run.json`, `result.json`), and keeps the newest 5 per session, without `src/` and `out/` once stopped. A run is the compose project `harness-<run>`: app and services sit only on an `internal` inner network with IPv6 off (no route out, online or offline; online calls go through the edge proxy, see Harness capture); the edge alone joins the outer network and publishes each app port on host `127.0.0.1` at a port Docker picks (`ports[].host_port`). Both compose builders, `review.Compose` and `harness.Compose` (with `compose_debug.go` and `compose_proxy.go`), build on `internal/sandbox`: its `Service`/`File`/`Network` types, the hardened `Workload` (read-only root, host uid, `cap_drop: ALL`, `no-new-privileges`, executable `/tmp`, `/src`, `/out` and the caches) and its `CacheInit` chown service, `NetworkOf`, `DisableIPv6` and `Marshal`; goldens under `internal/review/testdata/compose/` and `internal/harness/testdata/compose/` pin both outputs byte for byte (`go test ... -run TestComposeGolden -update` rewrites them). The edge runs this `aiman` binary (`aiman harness edge`, hidden, statically linked as release builds are) mounted read-only on `busybox:1.36` pinned by digest (`harness.EdgeImage`), with `ip_forward` off. Serve drives its relay map over `control/edge.sock`, a Unix socket in a 0700 directory only the edge mounts, with the per-run token in `control/token`. Images: the app image is `review.Image` of the exported tree (or `repos.<slug>.review.image`); the app and service images go through image vetting (below) and the run names each by the engine's image ID with `pull_policy: never`. The edge image (`harness.EdgeImage`) goes through the same vetting as a builtin (`harness.ImageRequest.Builtin`), so the first run on a host fetches, scans and loads it with no operator step. Without a vetter (`harness.Options.Images` nil; serve always wires one when the harness is on) app and service images must match `harness.allowed_images`, and every image, the edge's included, must already be on the host, else `harness_image_missing` with `data.image` and a message saying vetting is off; nothing is pulled then. A start runs the edge (first, so its proxy serves every later step), services (each `ready` probe up to 60s), fixtures, setup, `app.build`, `app.run`, then reads the edge's published ports, under 30 minutes in all, writing `run.json` and a log per step; the run goes `starting`, then `ready` or `failed` (`failed_step`, `failed_service`, `error`), then `stopped` (`stop_reason` `down`, `idle`, `session_gone` or `serve_restart`). Each run takes a subnet slot (inner and outer `10.231.<n>.0/25` and `.128/25`, debug `10.232.<n>.0/29`); a manager starts at a random slot (`Options.NetStart`) and takes the next free one after it, wrapping, and a start that Docker answers with an overlap moves on at most `netAttempts` (16) times.

Harness RPCs take `session` (id or name, default the caller) and, except up and list, `run`; a session caller passes `refuseOutOfScope` for the session or the run's session (`session_scope`). `harness.list {session?}` answers `{"type":"harness_list",session,source,sha,scenarios,runs,file_error?}`: a missing or broken file sets `file_error` `{code,message,data?}` and still lists the runs. `harness.up {session?, scenario, dirty?, force?, wait?, debug?}` (`HarnessUpTimeout` 2 minutes) answers `{"type":"harness_run","run":…}` with a `starting` run; `wait` holds the call up to 20s (`HarnessUpWait`) and turns a failed service into `harness_service_failed` (`data.service`, `data.tail`). It is in `pressureGated`: `force` passes a closed gate for the operator and is `needs_operator` from a session. `debug` starts a debug run (see Harness debugger). A dirty tree is `harness_dirty` (`data.paths`) unless `dirty`; aiman's own files (`.aiman_*`, such as the `.aiman_todo.md` a failing verdict renders) never make it dirty; a dirty run records HEAD as `sha` plus `diff_sha256` of the changes and untracked files, and its verdicts carry both. A review session runs the PR head (`review.State.HeadSHA`) with no clean-tree check. Other refusals: `harness_no_file`, `harness_invalid` (`data.errors`), `harness_unknown_scenario`, `harness_submodule` (`data.path`), `harness_too_large` (the memory sum is over `harness.run_memory`; `data.sum`, `data.limit`), `harness_running` (one live run per session), `harness_busy` (`harness.max_runs` live runs on the host). `harness.status` and `harness.result` (`harness_result`) take the run named, else the session's live run, else its newest kept run; `harness_not_running` when there is none. `harness.check {run?, name?}` (`HarnessCheckTimeout` 10 minutes, 5 per check) runs the checks on a `ready` run, each in a fresh container on the inner network (`compose run --rm --no-deps`): the app's, or for a check with `image` the compose service `check_<index>` (`harness.CheckService`, profile `checks` so `up` never starts it), a copy of the app's service (user, read-only root, mounts, env, limits) running that image by ID with `pull_policy: never`. A check image's memory is the app's limit and is not added to `harness.run_memory`, as a check in the app's image is not. It answers `harness_check` with each `exit` and redacted output tail; the tail (plain and debug checks) has escape sequences and docker compose's own progress lines (` Container … Creating/Started`, `[+] Running n/n`) removed (`checkOutput`). `harness.logs {run?, service, lines?}` answers `harness_logs` (default 200 lines, at most 1000) through `redact.Lines`, live or from the log saved at stop. `harness.down {run?}` (`HarnessDownTimeout` 2 minutes) runs compose down with volumes; the result files stay. `harness.verdict {run?, step?, result, note?}` is `needs_operator` for a session caller: step 0 (or absent) is the whole scenario, `result` is `pass`, `fail` or `skip`, and it works on a live or kept run. A `fail` adds or rewrites the to-do `Harness: <scenario> step <n>: <first line of note>` (`Ref` `harness:<scenario>:<n>`, `harness:<scenario>:all` for step 0) on the run's session, a review session included, and steers `[aiman] a tester marked harness scenario … fail at <sha>: <note>`; the reply's `todo` is that item's id. A verdict never closes a gate or the Done-when item. Every run call refreshes `last_used`; a reaper takes down a `ready` run unused for `harness.idle_timeout`. `dropSession` stops the session's live run (`session_gone`). Serve restart ends runs: `Close` cancels starts in flight and leaves containers, and the next serve's `CleanStale` takes down every run left `starting` or `ready` (`serve_restart`). Ledger kinds: `harness.started` (run, scenario, sha, dirty, diff_sha256, source, network, debug), `harness.ready` (run, ports), `harness.failed` (run, step, exit), `harness.check` (run, name, exit), `harness.verdict` (run, scenario, step, result, note, sha, dirty, diff_sha256), `harness.stopped` (run, reason), `harness.debug` (run, op, dropped client name). Config (`config.HarnessConfig`, pushed by `MarshalServeConfig`): `harness.enabled` (unset is on), `allowed_images` (default `postgres:16`, `golang:*`, `node:*`), `service_memory` (default 2G per container), `run_memory` (default 6G per run, clamped to `resources.session.memory_high`), `max_runs` (default 2), `idle_timeout` (default 2h). The gateway lists `harness.list`, `harness.status` and `harness.result` as device read methods; up, check, logs, db, down and verdict stay off the device list, so the phone only reads. CLI (`aiman harness`): `list`, `up <scenario> [--dirty] [--debug] [--force] [--wait]`, `debug [status|take|release]`, `status`, `check [<name>]`, `logs <service> [--lines N]`, `result`, `verdict <step|all> pass|fail|skip [--note TEXT]` (operator), `down`, and `console [--remote NAME] [--session NAME] [--run ID]` on the laptop, which opens `ssh -L` forwards to the run's relay ports (never `ssh -f`) and prints the URLs.

Harness web console (`internal/console`, `cmd/aiman/harness_console_web.go`; design rev 4, piece P2): `aiman harness console` on the laptop serves a web console unless `--text` (the P1e terminal console). It listens on `127.0.0.1` at a port the kernel picks, prints `http://127.0.0.1:<port>/#token=<token>` and opens it with `open` (macOS) or `xdg-open` unless `--no-browser`; ctrl+c stops it and its forwards. The token (32 random bytes, base64url) travels only in the fragment, which no request carries: the page moves it to `sessionStorage` and sends it as `X-Aiman-Console-Token` on every `/api/*` call (constant-time compare, else 401). It is never a cookie, because a cookie for `127.0.0.1` would also reach every forwarded app port. Every request, the static page included, needs `Host` exactly `127.0.0.1:<port>` or `localhost:<port>` (403 otherwise, against DNS rebinding); a POST also needs `Origin` `http://127.0.0.1:<port>` or `http://localhost:<port>` and `Content-Type: application/json`. No CORS headers; every answer carries a CSP (`default-src 'none'`, script, style and connect from `'self'` only (plus `ws://` to the console's own port for the debugger bridge), `frame-ancestors 'none'`), `nosniff`, `no-referrer` and `no-store`. The page (`internal/console/web`, plain HTML, CSS and JS through `go:embed`, no build step) sets every value from serve as text. The log (stderr) holds only refusals and failed requests by method, known path and status, never a header, query or the token. `console.Server` polls `harness.status` every 2s (the pinned run: `--run` or the last run it started, else the session's live, else newest run) and keeps the `HarnessForwarder` children in step: open while the run is `ready`, reopened when a child dies or the run changes, closed otherwise. API: `GET /api/state` (run, forwards, last error), `/api/list`, `/api/logs?run&service&lines` (default 200, max 1000), `/api/capture?run&after&limit` (default 50, max 200), and `POST /api/verdict {run, step, result, note}` (step 0 is the scenario), `/api/check {run, name?}`, `/api/up {scenario, dirty, force, debug}`, `/api/down {run}`. A run action naming a run other than the one shown is 409 `run_changed`; serve's refusals come back as 502 with serve's `code` and `message`, which the page shows as they are. Calls go through `usecase.ServeRPC` as the operator, waiting serve's limit plus 30s for up, check and down. The page shows the run header, app links, steps with pass/fail/skip and a note, checks with exit and output, a logs tab per container polled every 2s with a pause button, and up/down. Every `$` in a compose file's commands, environment and health checks is written as `$$` (`sandbox.EscapeInterpolation`), so compose passes it to the container instead of filling it from serve's environment. The console's methods (`harness.list`, `logs`, `capture`, `check`, `up`, `down`, `debug`, `files`, `file`, `db`, `evm_txs`, `evm_trace`, besides `status` and `verdict`) are on `aiman rpc`'s allowlist, which the RPC stream checks before it dials.

Harness console e2e (`cmd/aiman-harness-e2e`, build tag `e2e`; `e2e/console`): a driver that runs one web console against real Docker runs on this host, with serve in process (temp socket, sqlite database and harness directory, no image vetting), one registered session whose worktree is a fixture repository, and forwards that are the run's own host ports; several drivers can run at once. `--fixture` is `go`, `node`, `bun`, `python`, `vitest`, `vitest-bun12`, `db`, `sqlite`, `evm`, `evm2` or `net`; `--up` starts the run (`--debug`, `--debug-checks`, `--network online|offline`, `--attach-timeout D` for `harness.debug.attach_timeout`). Harness debugger (design rev 4 "Debugger mode" with the rev 5 lease and fixed addresses, piece P3; `internal/harness/debug_adapter.go`, `dlv.go`, `compose_debug.go`, `manager_debug.go`, `edge/dap.go`, `internal/server/handlers_harness_debug.go`, `internal/console/dap.go`, `web/debug.js`): `app.debug {lang, program?, args?}` in the file; `harness.up {debug:true}` picks the `harness.DebugAdapter` for `lang` from `Options.DebugAdapters` (Go and Node, below; another language is `harness_debug_unsupported`, and a file without `app.debug`, or an `app.run` that needs a shell when `program` is unset, is `harness_invalid`). The edge's `dap` relay (`--dap-relay`, `RelaySpec.Kind` `dap`) holds a lease: the first connection takes it, its initialize request's `clientName`/`clientID` name the holder (labels, not proof), and a connection that opens with the line `aiman-dap-lease <token>` (16-128 of `[A-Za-z0-9_-]`) lets later connections with that token join (at most `edge.MaxLeaseConns`, 8, for an adapter's child sessions); any other client gets a DAP error response naming the holder and is closed without reaching the adapter. Harness image vetting (`internal/harness/images`, `internal/server/handlers_harness_images.go`, `build/harness-scanner/`; design rev 4 "Image vetting and approval", piece P1h): `harness.Manager` asks `images.Vetter.Ensure` for every app, service and check (`checks[].image`) ref, and for the edge image with `Builtin` set. `HTTPRegistry` (registry API v2, anonymous or basic and bearer auth from the `auths` of `~/.docker/config.json`, no credential helpers) resolves the ref to the host platform's manifest digest without pulling; that digest keys `~/.aiman/harness/images.json` (`images.Store`, atomic writes under `images.lock`). Design publishing: `design.publish {session, file, key}` (`aiman design publish <file> [--key KEY] [--session NAME]`, session defaults to `$AIMAN_ID`) reads the file, which must be a `.md` file (by name and after symlinks) resolving inside the session's working directory or worktree, so an agent cannot publish `~/.aiman/config.yaml`; anything else is `invalid_params`. The handler runs under `server.DesignPublishTimeout` (3 minutes) and `CallRaw` waits 15s longer for `design.publish` (`callDeadline`; every other call waits 30s). A bad key or repo name (`design.ErrInvalid`) is `invalid_params`; any other publish failure is `publish_failed`. The key defaults to the issue key, else the branch with `/` replaced by `-` (`design.Key`). With `design.repo` set, `internal/design` keeps one checkout at `~/.aiman/design-repo/` (cloned with `gh repo clone`, or `git clone` for a URL or path), serialised by the file lock `~/.aiman/design-repo.lock`, which a waiting publish polls (`LOCK_NB`) until its context ends. Before the first publish to a GitHub repository (a slug or a github.com URL) in a serve process, `gh api repos/<repo> -q .visibility` must say `private` or `internal`, else the publish is refused; a local filesystem location (an absolute path, `./` or `../` path, or `file://` URL) is the only location not checked. A GitHub location is a slug or a github.com or www.github.com URL (https, ssh, `git@host:`), matched case-insensitively. Any other location, including a GitHub Enterprise host or a bare relative name, is refused with an error saying its visibility cannot be checked. `design.ExecRun` runs git and gh with `GIT_TERMINAL_PROMPT=0` under the request context. One `design.Publisher` is shared by the process; it remembers the repositories that passed. Each publish resets the checkout to `origin/main` (aborting a stuck rebase, discarding staged changes and unpushed commits), writes `<design.dir>/<repo>/<key>.md`, commits `design(<repo>): <key> rev <n>` only when the page changed (the revision is the count of commits touching the path), and pushes to `main`, rebasing and retrying up to 3 times; a failed push resets the checkout again. The result is `{"type":"design","design":{path,url,build,revision,local}}`: `url` is `design.site` or the GitHub Pages `html_url`, plus the path without `docs/` and with `.html`; `build` is `gh api repos/<repo>/pages/builds/latest`. With `design.repo` unset the page is written to `<git dir>/aiman-design/<key>.md` and the result has `local: true`. serve records `design.published` (revision, url, and accepted/rejected/deferred counts from the Decisions table, `design.CountTriage`). `session.create` and the dashboard never touch the docs repository.

Cost by role: `usage.get` accepts `by: role`, which buckets cost under the session's role (`reviewer`, `handover`, `consult`), else `child` when it has a parent, else `coordinator`. `usage_sessions` carries `role` and `parent_id`, COALESCE-protected like the other identity columns.

Steering queues notes for the agent: free text, or the formatted summary of someone else's list change. Notes the agent authored are dropped, as are changes that only touch `Ref` links. A window of 800ms collapses what arrived into at most two persisted notes (one for list ops, one for joined text). The queue is in sqlite, so a serve restart neither loses nor repeats undelivered notes. Delivery waits until the agent is at a prompt. `AgentEnded` holds the note (`ended`). A hook report of `idle`, or `waiting_input` from an idle prompt, opens the gate only when `HookStateAt` is after the last delivery. Other `waiting_input` is `dialog`. Anything else reported by the hook is `working`. With no usable hook report, only a high-confidence idle pane classification opens the gate, and only more than 3 seconds after the last delivery. A hook report calls `Kick` so a new state can release a held note. `session.forget` drops that session's steering queue. It does not delete `~/.aiman/todos/<id>.json`.

`handover.write` writes `.aiman_handover.md` in the session directory and stores the shared-context note `handover-<id>`. The reason is `archive`, `forget`, `restart`, `agent_switch`, or `pre_compact`. The file has a fixed skeleton: Goal, Constraints & Preferences, Progress, Key Decisions, Next Steps, Critical Context, Evidence, Verification. `handover.MissingSections` checks it; the content is derived from the active to-do, hook title/message, undelivered notes, diffstat and pane tail, and error/test lines stay verbatim. The file is written only when its bytes change. `handover.point` takes an optional reason and queues `HandoverRestartNote` or, for `pre_compact`, `HandoverCompactionNote`; it queues only when the file is already there. `PreCompact` writes the handover and queues the compaction pointer. A revive calls `handover.point`, so the note waits on the delivery gate instead of being typed while the agent is booting.

Each `handover.write` also starts a handover child (`internal/handoverchild`) when `handover.child` is on, the default. The mechanical write always happens first and stays whenever the child fails. Hidden roles (reviewer, handover) get no handover: `writeHandover` returns before writing. A session with no `AgentName` (a shell an agent opened with `pty create`) gets the mechanical file but no child. The child is a hidden ad-hoc session with role `handover` in the scratch directory `~/.aiman/handovers/<run-id>/`, a fresh repository. Run records are `~/.aiman/handover-runs/<run-id>.json`. The directory holds the inputs `brief.md` and `mechanical.md`; the child writes `handover.md`, `memories.json`, and `done` last. The brief names the transcript (`AgentSessionPath` at start), the worker worktree (read-only, may be gone), the reason, the eight headings and the JSON schema. It forbids code edits, commits, pushes, to-do changes, steering and child sessions. The child launches prompt-free, so that rule is not enforced; the scratch cwd is the only mitigation. `handover.write` may pass `agent`, the switch target. The child is that agent when it is installed, else the first installed `HandoverCandidates` entry (skipping the source when a target was named). A usage-limit switch therefore does not launch the exhausted source. A worker has at most one run: a trigger during a starting, running, or uncleaned run still writes the mechanical file, records its reason on the run, replaces the run's fallback render (mechanical text, sha, label, abstract), and starts nothing; the response's `child` is that run's id. When a new render's sha256 matches the run that last applied a child handover and the file's sha256 equals the file that run wrote (`LastApplied`), serve keeps the file, returns `written:false`, and starts nothing. While a run is active, `queueHandoverPointer` holds the pointer on the run (a later one replaces it), and the run queues it when it ends. A run ends `complete` when `done` exists, `incomplete` when the child ends or its terminal dies first, `timed_out` after `handover.timeout`, and `failed` when no candidate agent is installed or the launch fails. Only a complete run contributes outputs. A `handover.md` that fails `MissingSections` or exceeds 64 KiB is rejected, but valid candidates still count; bad `memories.json`, or one over 256 KiB, gives none. Both files are read through a size cap. At the end the run writes the child's handover to the worker directory when it exists, stores note `handover-<id>` (child text, else the mechanical body), and enqueues the memory job with the run id as its id; `memoryjob.Queue.Enqueue` ignores an id it already holds, so a retried finish queues it once. A gone worker gets no file and no steer; the note and job still go out, the note in the namespace from the group, issue key and repo the run captured at start (`handover.NoteNamespace`, shared with serve). Only `domain.ErrSessionNotFound` from the registry means gone. Any other lookup error leaves the run active, the pointer held and the child running, and the finish is retried. A finish runs on its own 30s context, so `Close` does not cut it short. An applied restart or agent_switch run queues `HandoverRefreshedNote` unless it released a held pointer instead. The ledger records `handover.child_started` and `handover.child_finished` (run, agent, reason, status, candidates, error). Cleanup stops the child, waits up to 30s for it to exit, forgets it, and removes the scratch directory. It also stops and forgets leftover handover-role siblings of the same worker so earlier runs cannot stack in `session.list`. `Resume` at serve start watches running runs again, fails starting ones with the mechanical fallback, releases the pointer and cleans up finished runs left uncleaned, and retires leftover handover children of workers whose newest run is already cleaned up. A starting run with no `ChildID` first adopts a child the last serve created but did not record: a `handover`-role child of the worker whose branch or directory is the run's (`ChildLister`, which `serverSessions` implements). Finish and `Resume` delete cleaned-up runs except each session's newest, which `LastApplied` reads.


Memory candidates are durable notes proposed from handovers and queued in serve (`internal/memoryjob`, `memory.jobs`, `memory.done`). A new job replaces the session's unfinished one. A child run enqueues its job at the end with its candidates. Without a child, serve enqueues the mechanical body only when the file changed. Admin Menu → **Memory candidates** fetches jobs from each remote. A job with candidates is shown directly. A job without them goes to Ollama (`ProposeMemories`) only when `ai.enabled`; otherwise the TUI marks it done. `a` accepts (a `context.put` under the job's group, else its repo), `e` edits, `d` drops, and the job is marked done once every candidate is decided.

The event hub (`internal/server/events.go`) fans each `Publish` out to every `session.events` subscriber. Each subscriber buffers 64 events. A full buffer drops the event, so a stalled client cannot block a socket handler. A to-do write publishes `todo_changed` with the list `Rev`. The steerer publishes `steer` with the queued count, and `DeliveredAt` once a note is submitted. The type names `usage`, `notify`, and `verify` are reserved on the same stream. Hub events are forwarded as they arrive. Each stream also polls once a second (`EventPollInterval`), reading the session table on that tick: `session_activity` per holder or state change, carrying `state` and `state_confidence` from `stateSweep`'s cache (no state until the sweep has sampled the session, and never for a hidden helper; the stream itself never classifies), `session_gone` once when a holder leaves the pty list, and `session_created` from serve's store (`collectRepoCreatedEvents`), sent again whenever a row's role, parent or name changes. The TUI drops a hidden-role row on `session_gone` and deletes it from the laptop DB; a visible child stays listed. After a scan of its host, the dashboard deletes a role-less laptop row named like a handover child terminal (`handover-<8 hex>`) that has no live terminal.

`session_events` is the durable append-only ledger behind the hub. `Server.appendEvent` writes one row (`session_id, seq, at, actor, kind, payload, hash`) and never fails the request; the sequence is allocated by the INSERT, and `hash` is sha256(payload). It records create, prompt, hook, handover and session-end facts (`session.created` carries `tier`, `requested_tier`, `model`, `effort`, `tier_fallback`), plus `pane.uncertain` (agent, backend, state and a sha256 of the cleaned pane, never its text) once per distinct pane `classify` reads at low confidence (the state sweep writes none); to-do, steer, verify, budget and review events join as their handlers land (`review.started`, `review.revealed`, `review.refreshed`, `review.approved`, `review.posted`, `review.run`, `review.coverage`, `review.fix_started`, `review.fix_pushed`, `review.fix_failed`, `review.assess_started`, `review.pr_approved`, `review.comment_ignored`, `consult.abandoned`). The table is never read on the request path and has no COALESCE rules. `session.log` reads it (`since_seq`, `limit`) and `aiman session log` is the CLI. The event hub is still the live stream; the ledger is the history.

serve runs the PR watcher (`internal/ciwatch`) in one goroutine. Every 2 minutes it asks `gh` about each watched session's PR. A failed check becomes the to-do `Fix CI: <name>` (`Ref` `check:<name>`) plus a steering note with the log tail, and a new inline review comment becomes `Address review: …` (`Ref` `review:<id>`). Only an `OWNER`, `MEMBER` or `COLLABORATOR` comment (`author_association`), or one whose author login is in `ci.trusted_logins` (matched ignoring case, `ciwatch.Deps.TrustedLogins`), does: any other is marked seen with no to-do or note and recorded once as `review.comment_ignored` (comment id, author, association, never the body). A check that keeps failing past 3 fix attempts raises a `ci_escalation` notification. Autonomous sessions are watched by default; `w` on the sessions tab toggles the watch through `ci.watch {session, on}`. `ci.get {session}` returns `{"type":"ci","ci":{…}}` and only reads serve's state. The TUI reads it on selection, on `todo_changed` for the selected session, and on a `ci_escalation` event. It shows `watching PR #<n>` on the meta line and turns an escalated row into needs-you. `aiman-trigger` never types into a pane: it calls `steer.send` with mode `note` for scheduled prompts. It never answers a dialog in an autonomous session; serve's notification sweep reports the `waiting_input` instead.

Notifications are `internal/notify`. Serve is the only writer of the log (sqlite `notifications`, plus `notify_last` for `min_interval` and `notify_cursors`). `stateSweep` (`runStateSweep`, `handlers_notify.go`) runs whether or not notifications are configured, every 2s (`sweepPeriodLow`) while the 1-minute load average (`readLoadAvg`, which is `hoststats.ReadLoadAvg`, the module's one reader of `/proc/loadavg`; elsewhere than Linux the period stays 2s) is below `runtime.NumCPU()` and every 5s (`sweepPeriodHigh`) at or above it, re-read each tick (`sweepPeriod`, `Ticker.Reset`); `Server.SweepSkipped` counts ticks skipped because the previous sweep was still running or ran past its period (a call that finds one running returns at once). One pass captures at most `sweepCaptureBudget` (16) sessions: transitions (the hook moved to waiting_input since the last pass, which `sweepMemos` remembers per session; the capture finds the menu behind it), then stale or missing hook reports, then fresh working reports (the menu check), then fresh idle reports while a recorder checks for a question, least recently captured first in each group; sessions past the budget are not sampled and keep their cached state, and a fresh report that answers alone, or an ended agent (transition or not), is sampled without a capture. For each sampled session that is not `Role.Hidden()` it calls `sampleState`, stores `{state, confidence}` in a per-session cache for the event stream, and observes the sample into the recorder when one exists; cache entries go when the session does and on forget. `handleReportAgentSession` feeds the same path (`observeState`), so hidden helpers never notify. `sampleState` has no side effects, and `classify` is `sampleState` plus the `pane.uncertain` ledger row, so the sweep never writes one. It answers an ended agent first, then a fresh hook report, then the screen rules. A fresh `working` report, or a stale one while `agenthook.TurnOpen` holds, loses to `pane.MenuOpen` (in the last 20 rows, a selected row, `❯` or `›` plus a number, with another numbered row in its list, only indented description rows between, and no composer or composer footer below it): that answers `waiting_input` at high confidence, in `session.list`, `session.prompt` (which refuses `agent_blocked`), `session.wait` and the sweep. A fresh `idle` report is never overruled. `steerReady` keeps its own hook-first order. `pane.AsksQuestion` finds the last composer row (`❯` or `›`, optionally inside Grok's box), walks up past blank rows, box rules, right-aligned status rows and the finished-turn marker, and reports whether the first prose row ends in `?`; a screen with no composer, which includes Pi, is false. A high-confidence `idle` that asks derives `NotifyWaitingInput` with the state left `idle`, so `session.prompt` still takes the reply and steering still delivers. The recorder counts only an ended agent and high-confidence states, primes each session's first observation without notifying, and enforces `min_interval` inside one transaction (`AppendIfDue`). A later observation with no kind clears the last one, so each new question alerts. Notification text never holds terminal text: the detail of a `waiting_input` is the hook's message when that report said `waiting_input`, else a fixed reason (`a menu is open`, `asked a question`, `waiting for confirmation`), and other kinds have none from the screen. Each append publishes a `notify` hub event with `Kind`. Other plans emit through `(*Server).NotifyRecorder().Emit`. `notify.since` (`after`, `limit`, `after: -1` for the tail) reads the log. Webhook and Slack sinks run in serve under cursor `serve`; `aiman-gateway` runs the same `notify.Dispatcher` over `notify.since` with only the phone sink and starts at the tail when it has no cursor. The TUI toasts `notify` events only when `domain.NeedsYou` (never `ended`) and does not refresh the pane for them. Config is `notifications` on the laptop with optional `remotes[].notifications`, pushed per host by `MarshalServeConfig(host)`. Never log the webhook URL, Slack token or Expo tokens.

`aiman slack` (`cmd/aiman/slack_*_cmd.go`, `internal/infra/slack`; design `docs/specs/slack-parity.md`) is a plain CLI that never calls serve. List cells map column names to `Col…` ids, option labels to choice values and text to `rich_text` (`internal/infra/slack/lists.go`). There is no drafts API. `aiman-gateway` (`cmd/aiman-gateway`, `internal/gateway`) is the phone's tsnet proxy, node `aiman-gateway-<host>` by default. A serving gateway holds the flock `~/.aiman/gateway.lock` (`gateway.LockInstance`), waiting up to 15s so a restart outlasts the old process; the CLI subcommands do not take it. It accepts the host token (`~/.aiman/gateway-token`, full access) or a device token from pairing (`~/.aiman/gateway-devices.json`, sha256 only). Device tokens pass `internal/gateway/allowlist.go` on `/v1/rpc`, deny by default; its test parses `Server.dispatch` so a renamed serve method fails it, and destructive methods need the device's `allow_destructive` (`aiman-gateway devices allow-destructive <id> on|off`; pairing leaves it off). That set holds everything equal to a shell on the host: `pty.input`, `pty.create`, `pty.run`, `session.create` and `session.restart`, beside `pty.kill`, `pty.forget`, `session.forget`, `review.post` and the agent updates. The terminal WebSocket needs the flag too, answering 403 before it dials. For a device without it, `todo.update` and `todo.remove` first read the list through `todo.get` (`internal/gateway/gate_todo.go`): closing, dropping, renaming or removing an item whose `Ref` starts with `gate:` is 403 and not forwarded, and a failed read refuses too. Reopening a gate, `todo.move` (it only reorders), other to-do edits, `session.prompt` and `steer.send` stay plain. A refusal the flag would lift keeps 403 and code `forbidden` and adds `data: {method, needs:"allow_destructive"}` (`needsDestructiveData`; a method off the allowlist entirely has no `data`). `gateway.restart_serve {}` (destructive, `internal/gateway/restart_serve.go`) is answered by the gateway without calling serve: it runs `remotesvc.RestartScript(serve)` detached (`Setsid`, nohup, log `~/.aiman/logs/restart-serve-gateway.log`; `Server.RestartServe` replaces it in tests) and answers `{type:"gateway_restart_serve",accepted,reason}`, `reason` `cooldown` within 60s of the last accepted call. `aiman-gateway pair` writes a single-use 5-minute code (`~/.aiman/gateway-pair-codes.json`, sha256, file-locked atomic writes shared by the CLI and the service) that `POST /v1/pair` redeems over the tailnet; pairing is refused on Funnel and locks for a minute after more than 5 bad codes. Never log tokens, codes, Expo tokens, or URLs carrying `access_token`. `api/openapi.yaml` is the phone contract; `internal/server/openapi_spec_test.go` fails when a dispatched method or published event type is missing from it.

Hosts update themselves (`internal/selfupdate`, wired in `cmd/aiman/host_update.go`; design `docs/specs/host-self-update.md`). Config is `host.update.mode` (`off`, `notify` or `auto`, default auto; an unknown value is notify) and `host.update.check_every` (default 10m, floor 1m), pushed by `MarshalServeConfig`; a host with no pushed config updates itself. Unless the mode is off, serve runs `Finish` and `Run`: 2 minutes after start and then every `check_every` it asks `remotesvc.LatestRelease` (ETag, `Ready()` once `checksums.txt` exists). A ready newer release is notified once per tag in notify mode and installed in auto mode. The gate defers an install while any `Busy` counter is non-zero, retrying every 30s: long calls in flight (`Server.Inflight`, the `slowCall` list in `client.go` that also sets `callDeadline`, minus `repo.list` and `aws.status`, plus `handover.write`), pending AWS device logins (`awslogin.Manager.Pending`), handover runs still starting (`handoverchild.Manager.Starting`) and running agent updates (`agentupdate.Manager.Updating`); after `MaxDefer` (30m) only long calls count. `ScriptRunner` writes `~/.aiman/tmp/host-update-<tag>.sh` and a wrapper and starts `nohup bash <wrapper>` with `Setsid`, logging to `~/.aiman/logs/host-update.log`; the wrapper renames `{"tag","exit","at"}` into `~/.aiman/host-update.result.json` whatever the exit. One settle path (`Finish`, the watcher after a start, every poll) turns the result into `ok` or `failed`, and `OnApplied` emits `host_update` once with an empty session id (`serve updated v0.34.0 → v0.35.0 on <host>`, `gateway updated v0.41.0 → v0.42.0 on <host>`, or the failure). State is `~/.aiman/host-update.json`, which the serve probe prints as `SELFUPDATE=` and `ParseProbe` reads into `Daemon.SelfUpdate`. The manager also keeps an installed `aiman-gateway` on serve's release (`Manager.ReadGateway`, wired as `readHostGateway`: `$HOME/.local/bin/aiman-gateway --version`, PATH only when that file is missing, plus `pgrep` for running). The read runs outside the operation lock under a 5s deadline and is cached 5s; a failed read or an unparseable version is `unknown`, never behind, and drift is `remotesvc.Outdated(gateway, serve)` only, so a newer gateway is left alone. A newer serve release keeps the serve script, whose lockstep carries the gateway. With serve at the latest tag and the gateway behind, or serve's last attempt at its own tag failed (a failed lockstep), the same gate, runner and result file run `remotesvc.GatewayRepairScript(serveTag)` (`set -e` plus the lockstep: install, restart only if it was running, never touch serve) as an `Attempt` with `Kind` `gateway` (`From` the gateway's version, `To` serve's tag; an empty kind is serve). A failed repair retries after the retry interval; `host.update` repairs at once (`reason` `gateway`). Notify mode calls `OnGatewayBehind` once per `<gateway>@<serve tag>` (`State.NotifiedGateway`). The host status stays serve's; a repair never makes it `updating`. A version that is not `vX.Y.Z` never updates itself. `host.version {}` (any caller, a device read method) returns `{"type":"host_version",host,version,protocol,latest,latest_ready,mode,status,checked_at,attempt,gateway}`, `attempt.kind` `serve` or `gateway`, and `gateway` `{installed,version,running,status}` (`current`, `behind`, `updating`, `failed`, `unknown`, `not_installed`; absent without a manager or reader); with no manager it is mode `off`, status `held`. `host.update {}` forces a poll and an install of a ready newer release through the gate and returns `{"type":"host_update",accepted,reason,target}`; a session caller gets `needs_operator`, no manager is `invalid_params`, and on the gateway it needs `allow_destructive`. CLI: `aiman host version [--json]`, `aiman host update [--json]`. The `notify` hub event carries the formatted notification in `text`. The phone sink pushes only `pushKinds` (`internal/gateway/notify.go`: waiting_input, ci_escalation, review_done, ended, error), so `host_update`, `agent_update` and kinds a newer serve adds are never pushed.

Daemon control (`internal/server/handlers_host_daemons.go`, `cmd/aiman/host_daemons.go`, design `docs/specs/daemon-control.md`): serve's `DaemonControl` (`Server.SetDaemonControl`; none answers `unavailable`) backs three RPCs. `host.daemons {refresh?}` (any caller, CLI `aiman host daemons [--json]`) returns `{"type":"host_daemons",host,daemons:[{kind,installed,driver,active,version,pid,started_at,rss_bytes,restart}]}` for serve (from its own process: pid, `/proc/self` start time and VmRSS, driver `systemd` when `INVOCATION_ID` is set), the gateway and the trigger (`remotesvc.StateScript`: `systemctl --user show` or the pid file's supervised child, `--version`, each under `timeout 2`; start time and RSS from `/proc/<pid>` in Go); rows are cached 5s unless `refresh`, and `restart` is the daemon's last operation, read fresh. `host.logs {daemon, lines?}` (CLI `aiman host logs <daemon> [--lines N]`) runs `remotesvc.LogsScript` (journal when the unit exists, else `tail` of `~/.aiman/<kind>.log`; the first line `AIMAN_LOG_SOURCE=` names it), default 200 lines, max 1000; every line passes `redact.Lines` (`internal/redact`: Slack tokens and webhook paths, GitHub tokens, LLM keys, Expo tokens, AWS key ids and secrets, Bearer, URL userinfo, `password=`-style values, PEM blocks and their bodies, and the gateway token by exact value, which `RedactValues` reads from `~/.aiman/gateway-token` per call), then each line is cut at 2 KiB and the oldest lines dropped past 256 KiB; the reply is `{"type":"host_logs",daemon,source,lines,redacted}`. Redaction protects the screen, not the permission boundary. `host.restart {daemon, force?}` (CLI `aiman host restart <daemon> [--force]`) calls `selfupdate.Manager.StartOperation("restart-<daemon>", force)` and returns `{"type":"host_restart",accepted,reason,daemon}`. Operations are the fixed names `restart-serve|gateway|trigger`: refused `busy` while any Busy counter is non-zero unless `force`, `running` while an operation or install is started. The started operation is saved as `State.Operation` (kind `restart`, `To` the name) in `host-update.json`, apart from `Attempt`, so `host.version` never shows it; while it is started, `host.update` is refused and auto-install waits, also in a fresh serve. `ScriptRunner` (`OpsDir` `~/.aiman/ops/`) runs it detached like an install, writing `~/.aiman/ops/<name>.result.json` and `~/.aiman/logs/<name>.log`, never the update result file; any other non-tag name is refused. `Poll`, `Finish` (which serve now runs in every update mode) and `Manager.Operation()` settle it. `remotesvc.RestartScript` restarts in place: `systemctl --user restart` when the unit exists, else it kills the nohup supervisor's children (`pgrep -P`) and the supervisor starts the daemon 2s later; it never rewrites the unit and never pkills. `host.logs` and `host.restart` are `needs_operator` for a session caller (checked before params), and a daemon outside serve, gateway and trigger is `invalid_params`.

SSH `systemctl --user` needs `XDG_RUNTIME_DIR` and the session bus; the scripts set those. Linger is enabled *before* `systemctl --user` so a first SSH to a host with no lingering user instance can still install.

Host budget (`internal/usecase/host_budget.go`, design `docs/specs/client-pileup-guard.md` P2): `Model.hostBudget` (`usecase.NewHostBudget(time.Now)`) gives each remote `HostBudgetSlots` (4) background and 4 foreground slots. A call that ends in a local timeout keeps its slot `HostBudgetCooldown` (60s). Class is by trigger: a key (selection bundle, `l`, `r`, `$`, opening a page) is foreground and waits inside its command (`budgetAcquire`); a timer or discovery scan (`resources.get`, git status tick, pane preview tick, `limits.get` and `agents.status` polls, daemon probes after discovery) calls `budgetTry` first, returns no command and sets no in-flight flag when none is free; a stream event (`todo.summary`, `todo.get`/`ci.get`/`usage.get` on an event) is skipped into `pendingFetch` and `drainPending` runs it from the next result handler. Actions (`ci.watch`, to-do writes, `steer.send`, restart, create, update) take no slot. `todo.summary` has a per-session guard (`summaryInFlight`), git status one per session (`gitInFlight`, remote part `gitStatusFetch`). `usage.get` and its `session.get` share one slot. `aiman rpc` allows `resources.get` and `agents.status|update|move_prefix`.

RPC stream (`internal/usecase/rpc_stream.go`, `cmd/aiman/rpc_stream.go`, design `docs/specs/client-pileup-guard.md` P1): `usecase.ServeRPC` is `Call` on a package-level `RPCStreams`, which keeps one `aiman rpc --stream` process per `RPCStreamKey()` (the ssh target), started on first use from `ssh.Manager.RPCStreamCommand()` (its own connection, `bulkSSHArgs("", false)`, so `ControlMaster=no` and `ResetControlSocket` cannot end it). A remote that is not an `RPCStreamRemote` execs per call as before (`execServeRPC`). The remote writes and flushes `{"stream":1}` before reading stdin, then reads `{"id","method","params"}` lines, checks `rpcMethods` before any dial, runs each call in its own goroutine through `server.CallRaw` (one socket dial each, so admission counts it) and writes `{"id","result"|"error"}` lines in completion order; at most 8 in flight, the ninth `server_busy` at once; EOF ends it. On the laptop a call waits for its id under its own deadline and a late answer is dropped. A timeout while the stream has written no line since the call was sent, or no hello by the deadline while the process runs, is a stall: the ssh client is killed and the remote is down 60s. A death after the hello, or ssh's own exit 255, backs off 1s, 2s, 5s, then 30s. While down, calls fail fast with `ErrServeUnreachable` and never exec. Only a remote command that exits with another status before the hello (an old binary, whose usage line matches no unsupported marker) marks the remote as having no stream, so its calls exec; `usecase.NoteServeVersion`, called from `applyDaemonProbe`, clears that when a serve probe reports a different version. `session.events`, `pty.attach`, preview capture and git status stay off the stream.

The cost column is `usage.FormatUsageCost` and is `-` when the row has no priced tokens. Unpriced model ids are listed under the table. Each host can show one dim extra line under its name; the usage view leaves that line empty.

## Session Restart

**Files:** `internal/ui/dashboard.go` (`restartSession()`), `internal/ui/restart_terminal.go` (`restartTerminal`)

The restart flow (triggered by `s` / `ctrl+r`, including switching agent):
1. Agent picker (same or different agent)
2. Serve writes `.aiman_handover.md`. An agent switch passes the target agent's command so the handover child launches as that agent. The agent-written `.aiman_session_summary.md` is only the fallback.
3. `PrepareSession` for the chosen agent (configured `--model` / effort flags, summary prompt). The same agent gets the session's `LaunchModel`/`LaunchEffort` as its pick; `adoptRestartAgent` clears them on a switch and `ClearNativeAgentIdentity` wipes them in the DB
4. `restartTerminal`: `usecase.RecreatePTYSession` replaces the agent process in serve's PTY runtime under the same session ID
5. `DeliverInitialPromptPTY` sends the handoff prompt

**The worktree is never touched.** Only the agent process is replaced.

The steps from the handover on are `usecase.RestartSession`, shared with serve's `session.restart`. The TUI passes its checklist directory and laptop database; serve passes its in-process `writeHandover`, this host's stored secrets and no checklist push.

A legacy tmux row restarts only after the user confirms they stopped it on the host (`LegacyStopped`); `s` on such a row shows the stop command first. A successful restart sets `Backend` to `pty`.

State captured at goroutine dispatch time (before the goroutine starts) to avoid data races:
- `s` (session copy)
- `workingDir` (from `s.WorkingDirectory`)  
- `remote` (from config)
- `sessionCfg` (copy of `m.sessionCfg`)
- `db` (`m.db`)
- `flowManager` (`m.flowManager`)

## Known Gotchas

1. **Bubble Tea versioning**: The project is fully on `bubbletea` v2 (`charm.land/bubbletea/v2`) with `bubbles/v2` and `lipgloss/v2`. Do NOT reintroduce v1 (`github.com/charmbracelet/bubbletea`, `/bubbles`, `/lipgloss`) — the type systems are incompatible and cannot coexist in one model graph. Key facts: key events are `tea.KeyPressMsg` (match via `.String()`; the space key renders as `"space"`, not `" "`); the alt screen and mouse mode come from flags on the returned `tea.View` (see `newView` in `internal/ui/views.go`), not program options; sub-models render strings via `viewString()` while only models handed to `tea.NewProgram` implement `View() tea.View`. Tests must build key events through `pressKey`/`pressRune` in `internal/ui/keystrokes_test.go` — never hand-construct key literals.

2. **SSH backgrounding**: Never use `ssh -f` from Go's `os/exec` — the child gets `SIGHUP`/`SIGKILL` when the parent handles signals. Use `ControlMaster=auto` + `ControlPersist` exclusively.

3. **Unix socket path length**: macOS limits Unix socket paths to ~104 chars. Keep paths in `~/.aiman/sockets/` short; `manager.go` hashes `user@host` to 16 hex chars to stay under the limit.

4. **`COALESCE` in Save**: Do not remove the `NULLIF(excluded.field, '')` guards from `repository.go` — the discovery cycle runs every few seconds and will silently blank out session fields if those guards are removed.

5. **`isRetriableSSHTransportError` includes "permission denied"**: This is intentional (handles intermittent SSH auth glitches) but means auth failures retry 4× at 30s each. A remote git denial (`IsRemoteGitAuthDenial`) is excluded. Do not change without testing.

6. **mutagen sync naming**: The canonical sync name is `aiman-sync-<session-ID>`. A pull-only transient sync uses `aiman-sync-<session-ID>-pull`. Older sessions may have `MutagenSyncID` set to something else — always terminate `s.MutagenSyncID` in addition to the computed name.

7. **Pane content compression**: `SessionSnapshot.PaneContent` is gzip bytes, not raw text. Always decompress before displaying or passing to AI.

8. **AWS credential expiry is read from the remote file, not STS**: every push records `x_security_token_expires` (`awsdelegation.ExpiryKey`) in the remote `~/.aws/credentials`, and `ReadCredentialExpirations` reads it back in one round trip. Profiles pushed before that existed have no key, so `RemoteCredentialExpiry.For` approximates from the file mtime plus `duration_seconds` and flags it as approximate — never present an approximate value as exact. All mint-and-push flows must go through `pushFreshCredentials` so the expiry keeps being recorded. `ApplyDelegatedCredentials` splices the profile's section (`spliceCredentialsSection`), and `RemoveSessionProfile` drops only the exact-case section (`removeCredentialsSection`), so other sections, comments, case variants and line endings keep their bytes.

9. **AWS credential messages are routed globally, not by view state**: `awsCredLoadedMsg`, `awsCredCheckResultMsg`, `awsCredRenewResultMsg`, `awsCredBatchRenewResultMsg`, `awsCredRemoveResultMsg` and `awsCredRenameResultMsg` are handled in `Update` *before* the `switch m.state` dispatch and forwarded via `routeAWSCredentialsMsg`. Renewals and probes are bubbletea commands that keep running after the user leaves the page; routing them by view state drops the results (the remote gets new credentials but the model never learns and never re-verifies). Do not move them into `handleAWSCredentialsUpdate`. For the same reason, the 30s repaint tick (`awsCredTickMsg`) is owned by the dashboard, not by `AWSCredentialsModel.Init` — per-visit ticks would stack one chain per page visit. `enterAWSCredentials` must keep a `Busy()` model rather than rebuilding it.

10. **AWS_PROFILE is sanitised, not trusted**: `usecase.SharedSessionAWSEnv` exports a profile only if it survives `SanitizeSessionAWSProfile` — legacy `aiman-<id>` names and names missing from `~/.aws` are dropped so the session falls back to the default credential chain rather than pointing at a profile that cannot resolve. Do not bypass it by setting `AWS_PROFILE` directly in the terminal environment code.

11. **`AgentEnded` is not cleared by `Save`**: `agent_ended` is COALESCE-protected, and an unset `AgentEnded` is written as an empty string, so saving `AgentEnded: false` leaves a stored `"1"` in place. `agenthook.ApplyReport` clears the in-memory flag only when a later report carries a lifecycle state and is not itself an end. A report with no state returns first and leaves the latch set. `handleReportAgentSession` (`applyAgentReport`) saves, then must call `Repository.ClearAgentEnded` when the flag flipped from true to false. That method writes `agent_ended = ''` directly. Dropping the call leaves the row ended after the process has reported it is alive. `ClearNativeAgentIdentity` also blanks `agent_ended`, but only as part of wiping vendor identity on an agent switch. It is not the report path.

12. **Teardown writes the forget handover first**: the TUI removes the worktree before it calls `session.forget`, so serve's own forget handover (`noteForgetHandover`) cannot write the file and fails by design. `terminateSaveContext` calls `WriteHandoverOnRemote(..., "forget")` at teardown step 0 instead, best effort with a 20s cap. That write starts the child too. If the child finishes after the worker row is gone, only the note and the memory job go out. Do not move the call after worktree removal.

13. **Session limits apply at terminal start**: a scope's limits are passed to `systemd-run` when the holder starts, so a session running before serve had scopes (or before a config change) is unscoped or keeps its old limits until it is restarted; `resources.get` leaves it out and `aiman resources --session` says it has no scope. `session.limits` changes a running scope, and `session.adopt_scope` (operator only) moves an unscoped running session into one. A new holder still joins by itself, before its command starts, so nothing forks outside the scope; `adopt_scope` is the only place serve moves processes that already run, and it re-lists the tree after each pass for that reason.

14. **`MemoryLow` on the serve unit needs its ancestors**: `memory.low` only protects against reclaim started at or below the nearest ancestor that also sets it. The serve and gateway units sit in `app.slice` under `user@<uid>.service`, which is root's to configure, so reclaim caused by the user slice's own `MemoryHigh` ignores them. What keeps serve responsive is that sessions are bounded below that limit (per scope and by `aiman-sessions.slice`). The user manager is delegated only `cpu memory pids`, so `IOWeight` is accepted and has no effect.

15. **The session TMPDIR lengthens socket paths**: `~/.aiman/tmp/<uuid>` is about 55 bytes longer than `/tmp`, and Linux caps a unix socket path at 108 bytes. Under it, tests that bind a socket below `t.TempDir()` fail with `bind: invalid argument` (in this repo: `cmd/aiman` todo tests, `internal/gateway` `TestSocketSourceReadsNotifySince`, `internal/ptyruntime` holders, and `internal/contextstore` `TestCollectAndImport`). Run them with `TMPDIR=/tmp`; new tests that bind sockets should use `shortTempDir`.

## Terminal runtime

Every session runs in the PTY runtime of the remote `aiman serve`. aiman never
starts, attaches to or stops tmux.

`internal/ptyhold` is the durable holder: `aiman pty hold` is a small process,
detached with `setsid`, that owns one PTY. Its state is files under
`~/.aiman/pty/<id>/` (`request.json`, `meta.json`, an append-only `spool`
rotated to `spool.old` at 8 MiB, `term.sock`, `resize`, `kill`, `exit`,
`activity.json`). `meta.json` also records the session's `role` and `parent_id` when the creator passed them. `internal/ptyruntime` is serve's thin client over that
contract. The serve unit uses `KillMode=process`, so stopping, restarting or
updating serve leaves holders and their agents running; the next serve finds
them again by scanning `~/.aiman/pty/`. Sessions also survive laptop
disconnects. A holder ends when its agent exits, on `pty.kill`, or on a host
reboot.

**Agent priority**: agents start at `nice 10` from `host.load.agent_nice`
(`config.HostLoadConfig.AgentNiceOrDefault`: nil is 10, 0 disables, clamped to
[0,19]). serve passes it to every pty it creates (`Server.SetAgentNice`): each
`pty.create`, including helper ptys a session creates, and the `review.debug` pty; `ptyruntime.Spec.AgentNice` reaches the holder as
`agent_nice` in `request.json`, and `childShell` runs the command as
`exec nice -n <n> bash -c <quoted command>` after the PATH and TERM exports. Builds,
tests, `git` and `ssh` inside a session inherit it. The holder itself is never
reniced, nor is a running agent; a request without `agent_nice` (an older serve)
runs the agent at the holder's niceness.

Socket API (`internal/server/handlers_pty.go`): `pty.create/list/get/input/
capture/resize/run/kill/forget` are plain JSON methods; `pty.attach` answers
once then takes over the connection: output streams out as raw bytes, client
messages are framed (`internal/server/attach_framing.go`, `[len BE][kind][payload]`,
kinds 0x01 input, 0x02 resize), which is what makes live window resize possible.

**Capture attributes**: `RenderScreen` and scrollback rows carry colour and dim
and no other text attribute. `third_party/vt10x` is a local fork (see the
`replace` note in `go.mod`) that tracks SGR 2 on the glyph (`Glyph.Dim`); SGR 22 and
SGR 0 clear it. `writeCells` opens a run with its own `\x1b[2m` and closes it with
`\x1b[22m`, at the latest at the row's last cell (before any `\x1b[0m`), so dim never
crosses a line. Claude's idle suggestion captures as `❯` NBSP
`\x1b[2m<text>\x1b[22m`, while typed text has no SGR. Text readers go through
`pane.StripANSI` (`Clean`, `Classify`, the composer check, notification text), so
dim changes only the screen hash (`ScreenHash`), which costs a client one full copy.

**Revive**: when a session's holder is gone (the agent exited or the host
rebooted), attaching revives it via `usecase.ReviveIfNeeded`. The agent
relaunches with its stored `LaunchModel`/`LaunchEffort` and its native resume
flag (sidecar id first, stored `AgentSessionID` as fallback; refuses if neither
exists so it never silently forks a fresh conversation).

**Boot wait**: `acceptWorkspaceTrustPTY` polls the new pty (budget 20) before
the first prompt is typed. Each poll checks, in order: a startup update dialog
from `infraAgent.UpdateDialogs` in the bottom `UpdateDialogTailLines` rows
(press its skip key, never Enter, and keep polling), a workspace-trust dialog
(Enter), then a ready composer. The outcome line is
`AIMAN_BOOTWAIT:<timeout|trust|ready|update>:<attempts>`. Codex's update menu
rows start with `›`, so the update check must stay ahead of `composerReadyRe`.
`UpdateDialogs` also holds Codex's "Hooks need review" menu, skipped with esc
(continue without trusting), and Codex's retired-model notice (`enter/esc
continue`, with no choice to make), skipped with esc so the session continues on
the replacement. Codex's splash shows `› Ask Codex` before any dialog, so a Codex
screen without its ` · ` model footer is not ready yet. A trust answer is sent
once and the loop keeps polling for up to `bootWaitAfterTrust` more rounds,
because Codex can draw that notice after trust; the outcome stays `trust` unless
a dialog was skipped. The shell matches the capture JSON with SGR removed
(`captureSGRFilter`) and `MatchUpdateDialog` strips it, because a style change can
fall inside a phrase.
After the first Return, the submit check reads the input box (the last row
starting with `›` or `❯`) and the rows under it, ignoring whitespace and `│`,
because Codex and Claude draw footer rows below the box.
`steerReady` holds `dialog` while a pty screen ends in one of those dialogs,
whatever the hook reports. Fixtures are in `internal/usecase/testdata/bootdialogs/`.

CLI (`cmd/aiman/pty_cmd.go`): `aiman pty list|create|get|capture|input|kill|
forget|attach`. Attach puts the local tty in raw mode and relays; ctrl+q
detaches without stopping the session. `--params-file` / `--file` flags keep
secrets and prompt text out of argv. `CreatePTYSession` writes the params file to
`$HOME/.aiman/tmp/aiman-pty-<id>.json`, mode 0600 in a 0700 directory, created empty
before the content goes in; both executors' `WriteFile` resolve the leading `$HOME`.

The laptop drives everything through SSH (`$HOME/.local/bin/aiman pty …`),
routed by `usecase.CaptureSessionPane / SendSessionPrompt /
TerminateSessionTerminal`. Call those rather than building pty commands.
`remotes[].session_backend` is ignored with a config warning.

**Legacy tmux rows**: a session created when aiman still ran tmux keeps
`Backend` `tmux` (`domain.IsLegacyTmux`). The row shows the badge
`tmux (legacy) · stop it on the host, then s`. Attach, revive, capture and
prompts refuse it with `domain.LegacyTmuxError`, whose `Hint` names the host and the
exact stop command (`tmux kill-session -t '=<name>'`); serve answers
`CodeLegacyTerminal`. Terminate leaves the tmux session to the user and still
removes the worktree after confirmation. `s` asks the user to confirm the tmux
session is stopped, then restarts the agent into pty. Non-test string literals
that run or name tmux live only in `internal/domain/legacy_tmux.go` and
`internal/ui/legacy_tmux.go`; `internal/usecase/notmux_guard_test.go` fails on
one anywhere else, and on any literal naming mosh.

## Session resource limits

Design: `docs/superpowers/specs/2026-11-12-session-resource-limits.md`. Linux with a user systemd only. `cgroup.Probe` (Linux, `systemd-run` and `systemctl` on PATH, `systemctl --user show-environment` answers; it sets a missing `XDG_RUNTIME_DIR` to `/run/user/<uid>`) fails with `ErrUnavailable` elsewhere, and serve then logs one line and spawns holders plainly: `resources.get` answers `supported:false`, and the TUI draws nothing.

**Scopes**: `wireResources` (`cmd/aiman/resources_wire.go`) sets `ptyruntime.Manager.Scopes` to the `*cgroup.Systemd`. `Manager.Create` asks `Scoper.Launch(key, limits)`: for a new scope it prefixes the holder command with `cgroup.RunArgv` (`systemd-run --user --scope --quiet --collect --unit=aiman-session-<id>.scope --slice=aiman-sessions.slice -p ...  --`), which registers the scope and execs the holder in place, so the pid, `Setsid` and the holder log are unchanged; when the scope still exists (a helper terminal, or a restart whose old processes linger) it returns the scope's cgroup directory, applies the limits to the running scope, and the holder moves itself there before it starts the command (`ptyhold.Spec.JoinCgroup`, `cgroup.Join`; a failed join is logged in `holder.log` and the command still runs; the kernel allows the move only when serve itself is inside the user manager's subtree, which it is under its systemd unit and is not under the nohup supervisor). `ptyhold.Spawn` returns `*LaunchError` when the spawned process exits non-zero with no exit file, and `Create` then retries without the prefix, so a failing `systemd-run` never costs the session. The cgroup path is `<user manager>/aiman.slice/aiman-sessions.slice/aiman-session-<id>.scope` (`Systemd.ScopeDir`); `ScopeName` replaces every character outside `[A-Za-z0-9_.-]` with `_`. Holders in a scope are outside `aiman-serve.service`, so a serve restart cannot reach them; the unit keeps `KillMode=process` for holders that run unscoped.

**Scope key**: `Server.scopeKey` maps a pty id to the session that pays for it: the id itself, or, for an id with no row that starts with `<stored session id>-`, that session (the longest match). `handlePTYCreate` and the `review.debug` pty pass it as `ptyruntime.Spec.ScopeKey` with `ResourceOptions.sessionLimits(key)`: the `resources.session` defaults merged with the session's override (`cgroup.Overrides`, `~/.aiman/session-limits/<id>.json`). `Limits.Merge` lifts `MemoryMax` to a raised `MemoryHigh`.

**Slice**: at start serve runs `systemctl --user set-property aiman-sessions.slice MemoryHigh=<n>` (`Systemd.EnsureSlice`, a persistent drop-in under `~/.config/systemd/user.control/`): `resources.sessions_slice.memory_high`, else `cgroup.DefaultSliceMemoryHigh` of the user slice's `memory.high` (that less a sixth, at least 2G; no limit when the user slice has none).

**TMPDIR**: `ResourceOptions.tmpEnv` adds `TMPDIR` and `CLAUDE_CODE_TMPDIR` = `~/.aiman/tmp/<scope key>` (0700) to `pty.create`'s env unless the caller set them. Claude Code's scratchpad and task-output base is `CLAUDE_CODE_TMPDIR`, else `TMPDIR` on Linux, else `/tmp`, then `claude-<uid>/<cwd slug>/<session>/`; `fileTranscripts.sessionDirs` therefore also accepts `~/.aiman/tmp/*/claude-<uid>/<slug>/<id>`. `forgetResources` removes the directory and the override from `dropSession` (forget and terminate), and from `pty.forget` for a terminal with no row that is its own scope key. A restart keeps both.

**Sampler and RPCs** (`internal/server/handlers_resources.go`): `Server.RunResources` runs a `cgroup.Sampler` every 10s over stored sessions and running rowless terminals (`resourceSessions`), reading `memory.current/high/max`, `memory.stat` (anon, shmem), `memory.pressure` (some avg10), `memory.events` (oom_kill), `cpu.stat` (`usage_usec` delta as percent of one core) and `pids.current` per scope, the same for the user slice and the sessions slice, and `/proc/pressure/{memory,cpu,io}`. `resources.get {session?}` (CLI `aiman resources [--session NAME] [--json]`, a device read method) returns `{"type":"resources","resources":{supported, at, host, user_slice, sessions_slice, sessions:[{id,name,…}], limits, slice_memory_high, tmpdir, missing}}` from the last snapshot; `session` narrows to that session's scope key, and `missing` names it when it has no scope. `session.limits {session, memory_high?, memory_max?}` (CLI `aiman session limits <target> [--memory-high SIZE] [--memory-max SIZE]`) stores the override and, when the scope exists, applies the merged limits with `systemctl --user set-property --runtime`; with no value it only reports. `session.create` takes the same two parameters (`--memory-high`, `--memory-max`): serve picks the session id first and stores the override before the terminal starts. Setting a limit is `needs_operator` for a session caller, and `session.limits` is off the gateway device allowlist. `session.adopt_scope {session}` (CLI `aiman session adopt-scope <target>`, `handlers_adopt.go`) moves a running session with no scope into one and returns `{"type":"session_scope",session,name,scope,moved,limits,warning?}`. `Server.scopeProcs` lists the scope key's running holders, what they run and every descendant (`procwalk.Parents`, `Descendants`), plus processes in serve's own cgroup that descend from no other holder and whose `/proc/<pid>/environ` has `AIMAN_ID` equal to the key (a daemon reparented to the user manager; only that one variable is read). `Systemd.Adopt` asks the user manager for the scope through `busctl --user call … StartTransientUnit` with the `PIDs` property and the limits (`systemd-run --scope` can only place itself), waits for the move, then writes stragglers into `cgroup.procs` for up to 5 passes; an existing scope gets the limits and the writes only. `moved` is 0 when everything was inside. It records `resources.adopted`, is `needs_operator` for a session caller, `unavailable` without a user systemd, `invalid_params` with no running terminal, and off the device allowlist. The session keeps its old `TMPDIR`.

**Scratch cleanup** (`internal/server/scratch.go`): `forgetResources`' caller `dropSession` also removes `<LegacyTmpRoot>/<any slug>/<AgentSessionID>` (`ResourceOptions.LegacyTmpRoot`, `/tmp/claude-<uid>` from `wireResources`) and the slug directory that leaves empty. The `review.debug` pty gets the session TMPDIR through `tmpEnv`. `Server.RunScratchJanitor` runs `SweepScratch` 10 minutes after start and then hourly unless `resources.scratch_janitor` is false (unset is on; `MarshalServeConfig` pushes the whole `resources` block). A pass walks only `TmpRoot`: it removes a directory whose name is no stored session (read from the repository, again before each removal), no running pty, no `<id>-` helper of either and no `aiman-ci-` run, and whose tree (symlinks ignored, never followed) was not modified in 24 hours. Plain files stay. It never reads or removes `/tmp/claude-<uid>`: a directory there may belong to a Claude the operator runs by hand. `host.stats` carries `scratch: {freed_bytes, last_run, legacy_bytes}`; `legacy_bytes` is the size of `/tmp/claude-<uid>`.

**Auto-adopt sweep** (`Server.adoptSweep`, `handlers_adopt.go`; design `docs/specs/client-pileup-guard.md` P0): `RunResources` starts `runAdoptSweep`, which runs 30s after start and every 5 minutes. For each running held holder it reads `cgroupOf(pid)` (nil means `cgroup.Of`); one outside `Systemd.SliceDir()` is adopted for its scope key through `adoptKey` (shared with `session.adopt_scope`, `Server.adoptProcs` nil means `Systemd.Adopt`) with `sessionLimits(key)`, and `recordAdopted` writes `resources.adopted` with actor `aiman` when something moved. It never runs without `Systemd`, and when serve's own cgroup is not under `Systemd.Root` (the nohup supervisor) it logs one line for the life of the Server and tries nothing. A failed adoption is retried every pass; the error is logged once per session and again only when its text changes. `resources.get` carries `unscoped: [{id, name}]` (computed at call time by `unscopedHolders`, also while adoption is impossible) and `serve_unit` (`Snapshot.ServeUnit`, serve's own cgroup, read by the sampler through `Sampler.OwnCgroup`). `aiman resources` prints a `serve unit:` line and one `unscoped:` line per session ending `restart to move its memory and scratch`: adoption leaves charged memory on serve's unit and the session's old `TMPDIR`.

**Pressure gate** (`internal/server/pressure.go`, `internal/cgroup/pressure.go`; design `docs/specs/client-pileup-guard.md` P3): `Server.RunPressure` (started from `cmd/aiman/serve.go`) calls `stepPressure` every 5s, reading the user slice serve runs in (`cgroup.UserSliceOf` on `/proc/self/cgroup`, so it works under the nohup supervisor and with `resources.enabled: false`): `cgroup.ReadPressure` (avg10 of `some` and `full`; no `full` line is 0) and `cgroup.SliceOverHigh` (`memory.current >= memory.high`). With no user slice it reads `/proc/pressure/memory`; elsewhere than Linux the read fails and the gate stays open. A failed read leaves the gate as it is and logs once per distinct error. The gate closes when `full avg10 >= 20` and opens after 30s in a row below 10 (`host.load.pressure_gate`: `enabled` unset is on, `memory_full_avg10`, `reopen_full_avg10`, `hold`; `SetPressureGate`, pushed with `host`); `some` and `slice_over_high` are reported and never close it. Harness memory (design harness rev 5, P7) also closes it: harness containers run under `docker.service`, outside the user slice, so the slice's pressure and `memory.current` never see them. `harness.RSSReader` (`internal/harness/rss.go`, wired by `wireHarness` through `Server.SetHarnessMemory`, read on each step under a 4s deadline) lists running containers whose `com.docker.compose.project` label starts with `harness-` (`docker ps` plus one `docker inspect` for their PIDs, at most every 15s or at once when a listed cgroup is gone), maps each PID to its cgroup through `/proc/<pid>/cgroup` (`cgroup.Of`, whatever the engine's cgroup driver) and reads held memory (`cgroup.ReadHeld`: anon plus shmem, never page cache) every step; `docker stats` runs only for a container whose cgroup cannot be read, once per listing. It groups by project into `harness.Memory{held_bytes, runs:[{run, project, held_bytes, containers}], source}`. The reading's `SliceHeld` (`cgroup.ReadHeld` of the slice) plus the harness total at or above the slice's finite `memory.high` closes the gate with `reason` `harness_budget`; it opens once that sum has stayed under 90% of `memory.high` and full avg10 under the reopen value for the hold. With no finite `memory.high` the harness memory is reported only. A failed harness read logs once per distinct error and keeps the last good one. While closed, `dispatch` refuses `session.create` (reviews and consults included), `review.run`, `review.coverage`, `review.fix`, `review.assess` and `harness.up` (`pressureGated`) before the handler (`pressureRefusal`) with `host_under_pressure` and `PressureRefusalData` `{retry_after_ms: 30000, memory_full_avg10, memory_some_avg10, since, reason, harness_held_bytes}` (`reason` is `memory_full` or `harness_budget`; `harness_held_bytes` only for the latter); the client does not retry it. `force: true` passes for the operator and is `needs_operator` from a session (always, gate open or not). `serverSessions.CreateChild` (verify reviewers, handover children) returns `ErrHostUnderPressure`, so a handover keeps its mechanical file and the run ends `failed` with `host under pressure`. `session.restart`, `session.terminate`, revive and `pty.create` are never gated. While closed the state sweep runs at `sweepPeriodHigh` (`Server.currentSweepPeriod`). Each closing logs and emits `domain.NotifyHostPressure` (`host_pressure`, NeedsYou true, empty session, `notify.Format` returns the detail `<host> is under memory pressure: full <n>%; new sessions, reviews and CI runs wait`, or for the harness budget `<host> is at its memory budget: sessions <n> plus harness runs <n> of <n>; new sessions, reviews, CI and harness runs wait`), at most once per 10 minutes by the gate's clock; each opening logs and runs the `OnPressureOpen` hooks. `Server.PressureOpen()` and `OnPressureOpen` are what a CI queue asks and is kicked by; `LastPressure()` is the last reading for a dump. `SetPressureSource(read, now)` replaces the reader and clock (tests). `host.stats` and `resources.get` carry `gate` (`PressureGate`, with `reason` while closed and `harness` (`HarnessGate`: `held_bytes`, `slice_held_bytes`, `budget_bytes`, `over_budget`, `runs`, `source`, `error`) on a serve with the harness), and `aiman host stats` prints `pressure: memory some <n>% full <n>%`, `harness: <held> held · with sessions <sum> of <budget>` with one line per run, and `gate: open|closed since <t>` (`closed (harness budget)` for that reason). The phone sink does not push the kind.

**Alerts**: `cgroup.Alerter` (sampler goroutine only) fires for a session whose held memory (`Usage.Held`: `anon` plus `shmem` from `memory.stat`, else `memory.current`; page cache never counts) stays at or above 90% of `memory.high` for 30s, or at once when pressure avg10 is over 50; it stays over until below 80% and 25, and repeats at most every 10 minutes. The user slice and the sessions slice fire on memory alone with no hold. `raiseResourceAlert` emits `domain.NotifyResources` (`resources`, NeedsYou true; with no session `notify.Format` gives `on <host> <text>`), records `resources.alert`, and enqueues `[aiman] this session is at <cur>/<high> memory[, pressure N%] and is being throttled|is close to its limit; reduce parallelism. Do not retry the same job.` through the steerer, except for a hidden helper. The phone sink does not push the kind.

**TUI** (`internal/ui/resources.go`): after each discovery result and every 10s while the sessions tab shows, the dashboard calls `resources.get` once per host with sessions (`fetchResources`, one request in flight per host). `resourcesMsg` and `resourcesTickMsg` are routed globally through `routeRemoteServiceMsg`. The selected session's meta line gains `5.2G/6G 150%` (`withSessionResources`: memory over `memory_high`, CPU of one core; warning colour at 90% or pressure over 50) and the header a `mem 18G/24G` gauge for the user slice of the selected session's host (`renderA1HeaderGauge`, dropped first when the header is narrow, absent without a finite `memory_high`). An error, `usecase.ErrRPCUnsupported` or `supported:false` removes the host's entry, so nothing is drawn.
